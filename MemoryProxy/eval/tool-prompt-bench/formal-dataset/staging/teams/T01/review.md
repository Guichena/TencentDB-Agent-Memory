# T01 Sol review

## Outcome

T01 is staged as a 40-case Dev Team fragment: 15 controlled positive/negative pairs plus 10 natural negatives. The five-pair retrieval-pressure pilot is retained unchanged except that its visible-asset-set hash is refreshed for the expanded Team asset set.

Positive family counts are Memory 6, Skill 6, and Knowledge 3. Memory assets contain the retained 12 L0 sessions plus 15 L1, 4 L2, and 1 L3. The Team has 15 real GitHub Skill packages and 3 fixed Knowledge assets.

## Luna batch review

The four existing DS02 Luna draft batches were migrated rather than regenerated. Their stale optional `raw_output_file` and `raw_output_sha256` fields were removed from the copied manifests; the canonical batch validator then passed Memory 4/4, Skill 4/4, Knowledge 2/2, and natural-negative 10/10.

One additional required batch, `t01-memory-assets-batch-01`, was generated by `gpt-5.6-luna` with high reasoning and no forked conversation. It wrote only its unique generator directory. Sol checked exact counts, ID uniqueness, the allowlisted source set, L2/L3 member references, and the three authoritative facts.

## Gold and production-route review

- Memory positives use two retained `tdai_conversation_search` cases plus one additional semantic `tdai_memory_search`, one exact-history `tdai_conversation_search`, and two direct `tdai_atomic_query` cases. Direct atomic queries expose their date/type filters in the public request.
- Skill positives contain two direct listed views, three search-then-`skill_view_by_id` sequences, and one listed view followed by `skill_files_read` for `resources/integration-testing.md`.
- Knowledge positives use `/tools/list` followed by `/tools/call`; their target fixtures are fixed to the selected T01 Agent and match the case workspace or policy scope.
- Every pair has one registered context-message delta, identical frozen fields, and a recomputed controlled-delta SHA256. Every negative has no-tool Gold with zero allowed calls.

The formal L1 schema represents the two durable operational decisions as `type=decision`, while the production atomic-memory endpoint names this runtime category `instruction`. `assets/memory.json` therefore preserves an explicit `runtimeTypeMappings` table and each affected L1 carries `runtimeType: instruction`; Gold keeps the production `type=instruction` filter. This mapping is an integration input, not a global schema edit.

## Source and visibility review

All 15 Skill targets/distractors are pinned to real GitHub files. Each source package records repository URL, a 40-character revision, source path, SPDX license, raw file SHA256, adapted file hashes, and an adaptation diff. Raw and adapted files are stored separately. Apache-2.0 and MIT license texts are frozen under `source-material/T01/licenses`.

The legacy author-only distractor label `candidate-d3-visualization` was not carried into staging because no such frozen T01 source exists. The pair's target is the real `pytest-coverage` package and its visible Team distractors come from the frozen 15-Skill pool. All other legacy Skill targets map directly to their source packages.

Bound/listed Skills are `discover-important-function`, `pytest-coverage`, `temporal-python-testing`, `analyze-ci`, and `uv-package-manager`. The other ten are current-Agent searchable/team-visible assets. No provider-visible case contains provenance, Gold, batch metadata, or target IDs.

No upstream repository was cloned, installed, or tested; only pinned source files and license texts were fetched for source freezing. No official patch or formal model run was produced.
